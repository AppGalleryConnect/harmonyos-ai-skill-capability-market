# 279-List组件首次创建布局时，Scroller控制器的跳转方法优先级变更为高于initialIndex的优先级

## 来源与版本

身份：扫描Rule ID 279。变更版本：5.0.2(14) Beta1。

[完整官方章节](../../changelogs/5.0.2(14)/os-api-behavior-changes.md#list组件首次创建布局时scroller控制器的跳转方法优先级变更为高于initialindex的优先级)（起始行441）；[官网原文](https://developer.huawei.com/consumer/cn/doc/harmonyos-releases/changelogs-for-all-apps-b123sp16#list组件首次创建布局时scroller控制器的跳转方法优先级变更为高于initialindex的优先级)。接口起始版本、行为版本与target隔离分别核对，不相互替代。

## 旧新行为

target≥5.0.2(14)时，首次布局前的scrollToIndex、scrollToItemInGroup、scrollEdge定位优先于initialIndex，改变初始化阶段两个定位来源的优先级。

## 影响条件与工程核查

沿List构造、Scroller实例、初始化调用链与数据到达时机核对是否同时存在initialIndex和首次布局前滚动，确认业务想要的首次可见项与对齐方式；后续用户滚动不能当初始化竞争。

## 受影响与不受影响示例

受影响：业务要求initialIndex指定项先显示，却在布局前发出另一定位命令。只有initialIndex、只有明确所需的滚动定位，或滚动发生在另一个已证实业务阶段时可无需修改；时序不明则补证。

## 最小方案与边界

如果业务要求初次显示 initialIndex 指定位置，优先消除初始化阶段的另一条定位命令；后续确有滚动需求时，再在可证明符合业务的时机执行。若原本就希望滚动命令优先，可保留并记录依据。不要把 onAppear、onDidBuild 或固定延时直接当“布局已完成”的通用证明，也不要删除用户触发的滚动功能。

## 验证与证据缺口

覆盖非零 initialIndex、对齐方式、分组、空列表、动态数据和后续滚动，观察首次可见位置与业务状态。只测最终停留位置可能漏掉初始化闪跳。 缺真实布局时序或窗口结果时分别记录缺口和待验证，不凭最终位置推定无初始化闪跳。
