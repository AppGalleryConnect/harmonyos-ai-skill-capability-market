# 283-Video组件不再默认解析并自动播放拖拽信息中的视频资源

## 来源与版本

身份：扫描Rule ID 283。变更版本：5.0.1(13) Release。

[完整官方章节](../../changelogs/5.0.1(13)/release-os-api-behavior-changes.md#video组件不再默认解析并自动播放拖拽信息中的视频资源)（起始行186）；[官网原文](https://developer.huawei.com/consumer/cn/doc/harmonyos-releases/changelogs-for-all-apps-b112#video组件不再默认解析并自动播放拖拽信息中的视频资源)。接口起始版本、行为版本与target隔离分别核对，不相互替代。

## 旧新行为

Video不再默认解析并自动播放拖入的视频资源。官方明确ROM 5.0.0.123引入，不把接口since10或应用target当作设备行为门槛，也不补造target隔离。

## 影响条件与工程核查

核对业务是否需要拖入即播放，沿原Video、onDrop、src、controller及已有准备/错误回调检查实际链路、数据类型、URI权限和切源管理。应用不需要此能力时不强行恢复旧默认。

## 受影响与不受影响示例

受影响：原业务依赖系统自动识别拖入视频并播放，未建立显式链路。无需修改：业务不要求拖入播放，或已有完整显式处理且满足需求。仅有Video组件、普通点击播放或单帧画面不足以证明本条需要修改或已验收。

## 最小方案与边界

在原链路显式完成“识别视频记录→更新src→准备完成后启动”。下面是已有 Video 属性链的事件处理片段；videoSrc/controller 是原组件字段，另有普通字段 pendingDroppedVideoUri: string | undefined，初值 undefined，用资源URI记录本次有效拖入的播放意图。此片段只展示单次拖入链路，复杂切源须复用工程已有资源状态管理。LOG_DOMAIN/LOG_TAG 和 hilog 由工程既有日志约定提供，统一数据类型从 @kit.ArkData 导入 unifiedDataChannel、uniformTypeDescriptor：

```ts
.onDrop((event: DragEvent) => {
  try {
    const records = event.getData().getRecords();
    for (const record of records) {
      if (record.getType() === uniformTypeDescriptor.UniformDataType.VIDEO) {
        const video = record as unifiedDataChannel.Video;
        if (video.videoUri.length > 0) {
          this.pendingDroppedVideoUri = video.videoUri;
          this.videoSrc = video.videoUri;
        }
        return;
      }
    }
  } catch (error) {
    this.pendingDroppedVideoUri = undefined;
    hilog.error(LOG_DOMAIN, LOG_TAG, 'Read dropped video failed: %{public}s', String(error));
  }
})
.onPrepared(() => {
  const pendingUri = this.pendingDroppedVideoUri;
  this.pendingDroppedVideoUri = undefined;
  if (pendingUri !== undefined && this.videoSrc === pendingUri) {
    this.controller.start();
  }
})
.onError((error) => {
  this.pendingDroppedVideoUri = undefined;
  hilog.error(LOG_DOMAIN, LOG_TAG, 'Video loading failed: %{public}s', String(error));
})
```

原组件构造字段是 controller，不是 ontroller；不直接取 records[0]、不把图片/文本当视频、不在资源尚未准备好时调用 start。getData 的读取异常须有明确处理，复用工程原错误边界，不吞掉无关业务失败。取消拖入或切到非拖入来源时，须在原入口先清空 pendingDroppedVideoUri，再执行原切源逻辑，不能等下一次准备回调。加载失败时清理意图并保留原错误反馈。同源重复拖入不能假设每次赋值都会重新触发准备回调；连续异步切源还需关联实际资源身份或串行协调，不能仅比较当前URI就证明某个回调属于本次资源。如果原业务已有 onPrepared/onError 或自动播放条件，应合并处理，不能覆盖原回调或让所有来源无条件自动播放。

## 验证与证据缺口

视频、非视频、空记录/不可读取数据、拖入加载失败后普通切源、取消、快速连续切源和既有控制事件分别测试；核对 onDrop→src→onPrepared→start，保留原资源权限和失败反馈，不能只以播放器显示一帧作为完整通过。 数据读取、来源身份或原有回调不明时列具体缺口；无设备结果不标播放通过。
