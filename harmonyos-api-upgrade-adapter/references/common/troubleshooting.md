# 失败处理、断点继续和安全撤销

本页说明定位、尝试、证据有效性、继续和撤销的方法。具体等待节点、返回步骤和下一步由当前功能主流程负责。遇到问题先保存实际输入、未截断命令、cwd、stdout/stderr、退出码和当前差异，再决定返回哪个步骤；不改原CSV、SDK、知识或结果分母绕过问题。

## 定位与停止

| 情况 | 保存与核对的方法 |
| --- | --- |
| 范围/版本/声明不明 | 保留实际候选及缺失证据；局部缺口不阻断独立单元 |
| 授权/方案待答复或实质变化 | 保存原方案、真实答复与变更范围；按当前主流程确认，不以超时或初始自动请求代选 |
| 行为原包归档受阻 | 保存构建、签名或归档原因及原源码/配置，暂停相关修改并等待补齐或明确改变验证方式 |
| 原包已归档但设备/用例受阻 | 保留有效 before 包和具体测试缺口，可继续获批修复，不声称已经取得 before 实测证据 |
| SDK/IDE不足或路径无效 | 保存真实元数据与已检查路径，不默换SDK或把Beta当Release |
| 扫描超时/INCOMPLETE | 保留JSON、coverage、diagnostics与可信部分，不用grep冒充扫描 |
| 代码/ArkTS错误 | 阅读真实 build error、准确声明及依赖，按[案例索引](../upgrade/scanner-missed-cases.md#按错误或异常检索)查找可能原因，核实后只修必要范围 |
| 依赖/签名/安装/进程/超时 | 保存实际退出码、日志尾部及连接/签名状态；仅阻断条件变化后重试 |
| HDC_READY或目标歧义 | 保存真实target列表和实例映射，不换设备、不强停已有实例 |
| 产物缺失/陈旧 | 核对本次任务、product/target、日志和生成情况，不沿用旧包 |
| 功能失败/视觉模型中断 | 分别保存结论；截图不替代功能，中断不冒充缺陷或通过 |
| 验证后SDK/配置/源码变化 | 保留原证据，核对新身份及影响范围，相关旧成功标待复核 |

每个实际错误及受影响的源码/依赖范围独立记录尝试。最多三种实质源码失败方案；同一失败输入不原样重试，第三种失败或连续三次无实质源码进展就停止该修复，继续独立组或交付可信部分。格式、空语句、日志文字、扩大范围或改错误消息不算新方案；另一个错误消失不重置仍失败错误的次数。

环境、依赖、网络、签名、工具崩溃和超时不消耗源码方案次数，但不能在相同确定性阻断下空重试。不设隐性总体时间上限；遇到可验证新条件再继续。记录失败方案、真实原因和下一步，不需要事务账本或自动预算状态机。

## 按报错或明确异常查阅案例

只有出现真实编译/构建错误，或用户明确报告混淆失效、发布包异常时，才按[漏扫案例](../upgrade/scanner-missed-cases.md)检索相关条目；不在正常扫描、CSV零行或构建成功时主动通读、核查全表，也不把缺少固定报错的混淆变化编造成 build error。

保存完整日志，从错误主句、错误码、符号/类型和文件位置提取线索；只有 BUILD FAILED、任务失败或退出码时先找实际诊断。用户报告产物异常时核对真实构建模式、工具链和产物身份。按本页索引得到的只是候选原因，须回读准确官方说明、SDK及工程依赖验证，未匹配则继续常规排错，不强行套用。

同一获批方案内的必要实现修正可沿用批准；新增业务方案、模块依赖、共享配置或修改范围须按当前主流程更新方案并确认。没有CSV对应行的问题只记录在实际编译日志、现有进度和报告说明中，不生成扫描行/rowId或改变原始行统计，不添加补充候选协议。原包归档、重建和失败次数仍按原规则处理。

## 断点继续

1. 读取轻量progress总览、当前分组、原CSV与来源身份。核对工程/product/版本/范围，没有把adapted副本当较小原基线。
2. 回读当前实际文件和已存在diff，核对相关SDK声明、配置、包与证据是否仍对应。模型自己写过“完成”不是验证凭据；输入或相关文件变化时将对应结果改待复核，保留原说明。
3. 核对结果行与原始逻辑行/重复记录、实际答复与方案批准范围。工程/product/目标/范围及方案仍适用时沿用已明确选择，不逐文件重问；旧记录缺必要目标、批准或已要求的验证范围时只补缺项，不默认已批准。部分批准只继续获批项；实质方案变化重新确认受影响部分。行为已选对比且原包构建/签名/归档仍受阻时维持暂停相关修改，不能自行改为仅after；原包有效归档后的设备阻断只影响测试，不阻止获批修复。行为批准以当前 spec 为依据，全部评估返回后方可汇总确认；已停止的错误不通过新目录或重置尝试绕过。
4. 旧版本的manifest、model-store、source-state和报告只作只读来源；不解析继承旧账本、不迁移其凭据、不把旧Fixed/编译PASS当当前成功。需要处理时从原始扫描及当前工程重新评估。
5. 保留用户改过的报告、源码和历史证据。未知来源的签名/配置变化先说明，不刷新原事实来消除冲突。

无法证明原输入或修改归属时，明确缺口并交付可信部分。行为缺原包时保留基线缺口，不回退工程制造before；废弃仅核对当前包，不产生before门槛。

## 安全撤销

失败默认保留当前源码和诊断，先修复必要片段，不自动整文件回滚。只有用户明确要求撤销时：读取当前文件、原任务差异及后续编辑，定位本任务可证明归属的片段；仅撤销这些片段并复核其他内容。共享helper仍被其他已完成修改使用时不能删除。

存在未知归属、重叠后续修改或用户同文件编辑时，保留现场并说明无法安全自动撤销的范围。不要使用整仓checkout、stash、换行重写、复制旧文件或伪造哈希覆盖用户改动。

## 部分交付

任何阻断都不免除当前功能流程的覆盖核对与交付。保留全部原始行，分别填写当前模型结论、工具实际结果、停止原因和待补证据；未构建、未运行及本功能实际要求的其他未验证项各自写明，不用“全部完成”掩盖。文件实际存在、可回读并带完整路径后再回复。

源码或构建配置已修改，但缺少当前输入对应的真实编译成功时，必须明确部分完成/待编译或编译失败。允许交付可信修改和分析，MODIFIED不代表已验证完成；环境修复后按当前主流程重新完整构建，代码或SDK再次变化时重新检查受影响结果，不沿用旧成功。

## 待处理计数的只读定位

已有任务出现pendingCount时，先读csv validate返回的pendingGroups，再用同一task/project/mode的validate --details --output保存明细。按pendingFields核对实际outcome、next或待分类状态；不依赖grep "PENDING"、不解释为缓存、不用临时Python推测JSON结构。工具读取当前文件且不改写判断，后续业务处理仍回当前主流程。
