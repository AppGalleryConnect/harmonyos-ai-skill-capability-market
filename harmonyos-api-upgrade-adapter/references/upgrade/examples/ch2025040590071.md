# CH2025040590071-播放器所使用的内存归属变更

## 来源与版本

身份：扫描Rule ID `CH2025040590071`。

依据[官方完整章节](../../changelogs/6.0.0(20)/beta1-os-api-behavior-changes.md#播放器所使用的内存归属变更)（817–848行）。6.0.0(20) Beta1起，仅应用`targetSdkVersion ≥ 6.0.0(20)`生效：AVPlayer内存缓存从系统侧计入创建播放器的应用。章节起始API Level 9是AVPlayer起始版本。

本地API 26 SDK的`openharmony/ets/api/@ohos.multimedia.media.d.ts:61,86`提供createAVPlayer回调与Promise重载；2234–2256声明pause仅playing状态可调用，2306–2328声明release可在除released外任意状态调用且Promise为`Promise<void>`。声明表明暂停与销毁是不同操作，不能把暂停统一视作实例不再使用。

## 旧新行为

变更的是内存归属，不是播放接口参数或pause/play语义。新归属可能增加应用被统计的内存，从而影响高资源使用场景的后台RSS管控。官方说明正常使用（同时工作的实例少于16）无需变更；超出正常范围应按实际使用调整实例数量，避免后台RSS查杀。

16是该章的正常使用指导边界，不是公开的硬性创建上限，也不是“16个必杀、15个绝对安全”的保证。不能把“同时创建”或“列表长度”直接等同“同时工作”，也不能因此忽略长期保留的预加载/暂停实例及实际内存。

## 影响条件与工程核查

核对打包target，查所有createAVPlayer入口、封装池、预加载和页面/服务生命周期；建立实例身份到用途、状态、持有者、创建、交接和release的时间线。统计同一时刻工作的实例峰值，兼查仍占用资源的缓存实例，分析快速滑动、并发创建未完成、页签切换和后台播放。

证据包括峰值及采样口径、实例状态、内存/RSS趋势、退后台日志和查杀原因、业务是否要求恢复位置或持续后台播放。只有create调用次数、播放器数组长度或一次静态快照，不足以证明并发工作数量；未记录release完成也不能把发起释放当作资源已回收。

少量正常工作实例、生命周期清楚且无新增风险的场景可无需适配。低target可排除本条归属改变，但不等于其资源管理没有别的问题。并发数量、所有权或后台需求不清时记录证据不足，不能强制全量释放。

## 受影响与不受影响示例

受影响例：视频墙target从19升20，持续同时工作的AVPlayer为20个，所有离屏卡片仍播放，后台内存证据显示播放器资源占比明显上升；已有业务只要求当前4个可见视频播放。可局部收缩活跃窗口，对确认不再使用的实例从池中退役后释放。

以下是已有资源管理器的异步清理片段，`retiredPlayer: media.AVPlayer`已经解除持有与事件使用，且确认不是released、不会恢复播放；异常沿用工程原处理：

```ArkTS
await retiredPlayer.release()
```

无需修改例：同时最多3个播放器，其中暂停的主播放器要在用户返回后续播；正常所有权及离页释放已有证据，低并发播放回归正常。暂停态不代表应销毁，销毁后不能直接对同一实例play续播。

## 最小方案与边界

先优化确有冗余的并发/预加载窗口和实例所有权，复用或有界管理播放器，等待释放完成后更新计数。保留必要的背景音频、暂停恢复、播放位置和Surface等业务契约；退后台是否保留由业务决定。对已退出且不再使用的实例及时释放，处理重复退出、异步创建返回过晚和并发release。

不要把“所有暂停播放器”“所有退后台播放器”统一release，不降低target逃避统计，不虚构修改RSS阈值的应用接口。若业务确需高并发，给出并发、媒体规格和内存实测后讨论资源预算，不能只改一个小于16的常量就宣称绝对安全。

## 验证与证据缺口

测试顺序播放、快速滑动、预加载取消、暂停后恢复、seek、页面销毁和后台音频；在相同媒体和设备下记录峰值活跃实例、保留实例、release完成、RSS曲线及后台存活/查杀原因。排查未完成创建泄漏、重复释放和释放后回调触及旧实例。

本案例真实编译、实例监测、内存测量及设备后台验证均未执行。缺峰值口径、业务所有权或查杀证据时为证据不足；不得把没有复现查杀写成“不会被RSS查杀”。
