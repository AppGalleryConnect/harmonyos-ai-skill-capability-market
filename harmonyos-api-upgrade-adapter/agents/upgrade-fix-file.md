# 单个物理文件的获批行为修复

供[行为主流程 U06](../references/upgrade/upgrade-workflow.md#u06-实施获批修复)调用。文件少时主 agent 直接按本说明处理；文件多时按物理文件分派。

**职责。** 一个修复者负责一个物理文件（路径别名归为同一文件），一次处理完该文件涉及的全部获批变更。按文件而非按变更划分，是为了让每个文件只有一个修改者。

**可写范围。** 只修改分配到的这个文件。共享 spec、总进度、报告、其他文件和配置由主 agent 负责；需要新建公共 helper 或涉及未明确的共享依赖时，交给主 agent 协调。

遵循主流程的[通用原则](../references/upgrade/upgrade-workflow.md#通用原则)，其中与修复最相关的是：只做获批范围内的最小修改，证据分层表达。

## 输入与进入条件

- 一个明确的物理文件，以及这个文件涉及的全部已批准变更、rowIds 和具体方案。
- 当前 spec.md 的路径/相关内容、实际批准范围及来源。有批准才实施修复。
- 对应完整官方章节、准确 SDK、工程/product、原/目标 target、compatible 和业务约束。
- 任务外改动、主 agent 协调的共享 helper/配置/跨文件接口及各自修改归属。
- 已确认的验证方式。选择对比时，主 agent 已核实修改前的 before 包有效归档。

任何一项进入条件缺失时，先向主 agent 报告并等待补齐。

## 修复步骤

1. **核对当前代码与方案。** 阅读文件及相关官方完整章节。新增或替换调用时核对准确 SDK 和必要调用链，包括同步抛错、Promise 拒绝、获取失败及回调失败，确认处理边界、业务失败出口，以及当前输入仍支持获批方案。保留用户与其他任务的改动。来源不明或实质方案变化时，交回主 agent 更新 spec。SDK 声明按[评估说明的定位表](upgrade-assess-change.md#sdk-声明的位置与检索)直接打开对应目录或文件。

2. **实施最小修改。** 同一文件的全部获批变更一起处理，默认保持原功能、视觉与交互。
   - 按[编码规范](../references/common/arkts-coding-standards.md)保留返回/回调、同步异步、异常、资源身份和生命周期。
   - 按[行为兼容](../references/upgrade/upgrade-compatibility.md)采用确有必要的显式参数或新旧分支。compatible 保持原值。
   - 每处修改都对应一条获批方案的业务目的。扫描是否还会命中不作为修改理由。
   - HAR/原生按对应专题处理。

3. **复核实际差异。** 逐处检查 diff：
   - 每处差异对应哪条获批条目及 rowIds；import 无重复；格式和日志保持原样；获批调用点全部改到。
   - 按[新增调用规则](../references/common/arkts-coding-standards.md#新增调用的废弃状态)逐项核对本次新增/替换的调用、helper 及获取链的准确 SDK 声明，使用未废弃的 API。官方旧例核验后再用。
   - UIContext 取自当前组件/窗口，或沿已有调用链传入。绘图上下文是另一种对象。
   - 替代能力或最低版本不满足时，返回缺口/取舍，compatible 和告警配置保持原样。原有的无关废弃代码保持原样。
   - 只有与该行相关的实质修改才算该行的修复。仅根 target 变化或同文件的无关变化，对该行返回“无需修改”的具体依据。
   - 失败契约：对 diff 中新增或替换的调用、获取链和 helper 核对有效异常处理，已有外层 catch 可复用。框架回调内部的异常在其实际执行边界处理；未 await 的 Promise 有实际拒绝处理或向有效消费者传播。保留原返回值、后续语句、回调次数和资源释放，失败时走真实的业务失败出口。确认为不抛异常的同步 API 直接调用。检查范围是本次改动及必要链路。

4. **执行可用文件检查。** 按[真实静态检查](../references/common/verification.md#通用静态复核)执行实际可用的 SDK/IDE 检查，分别报告模型复核、工具未执行、历史诊断和新增诊断。
   - 核查与 diff 相关的新增废弃告警。这项核查独立于构建结果。
   - 返回真实声明和替代选择的证据；无法确认时保留缺口。
   - 检查失败时只修必要闭包，保留当前差异和诊断供主 agent 判断。
   - 完整工程构建由主 agent 统一组织。

5. **返回结果。** 返回以下内容，由主 agent 统一落盘：
   - 物理文件、关联方案/rowIds、真实修改及必要前后片段或哈希、业务理由。
   - 实际检查命令/退出码/日志、未完成项和需要主 agent 协调的内容。
   - 四项材料：新增调用、SDK 失败契约、处理位置、复用或新增的处理方式。引用准确声明及实际代码位置；同一边界可合并说明多个调用；不抛异常或契约未明时据实注明。
   - 具体修改、作用及理由，供主 agent 填入行为 CSV 的处理说明。未编译、编译失败及实际所需人工验证写入后续事项。

内部 MODIFIED 表示相关代码已改；构建和设备验收的状态由后续证据另行给出。主 agent 从分组生成评估结论和处理结果表，并按 U07 核实四项材料后追加 resolution.review 及验证记录，原评估 reason/evidence 保持原样。

失败和受影响范围由主 agent 按[排错方法](../references/common/troubleshooting.md#定位与停止)协调。同一错误的实质失败次数跨 agent 累计。
