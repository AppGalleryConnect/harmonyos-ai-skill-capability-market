# 行为变更完整适配流程

按 U01–U09 执行：扫描整理 → 按变更评估 → 确认 spec → 修复 → 按需处理DevEco规则包未覆盖条目 → 构建与按需测试 → 交付。评估与修复分离，默认尽量保持升级前的功能、视觉和交互体验。处理 API Behavior Change、UX Visual Layout Change、UX Interaction Behavior Change 及 API Definition Change，支持 HAP、明确模块/目录的 HAR 和相关 C/C++。RNOH（React Native for OpenHarmony）工程在 U04 后追加 U04a，补充评估扫描器覆盖不到的框架层与 JS 层。

行为按[官方行为边界与 target 隔离](upgrade-compatibility.md)处理跨系统差异。本流程的范围固定为：按官方触发条件判断行为变化，compatible 保持原值，扫描只做一次。通用接口版本可用性匹配、调整 compatible 和行为复扫属于范围外。scanner 提供扫描事实，模型负责业务判断。

## 通用原则

各步骤都遵循以下六条原则，步骤内只写该步骤特有的做法。每条原则后附原因，遇到步骤未覆盖的情况时按原因推断。

### 一、每类证据只证明它自己那一层

适配是否正确需要多层证据共同支撑。记录和报告时按下表分别表达，缺哪一层就保留哪一层的缺口。

| 证据 | 能证明 | 记录为 |
| --- | --- | --- |
| 扫描命中、CSV 字段齐全 | 存在需要评估的调用候选 | 原始行 |
| 扫描零行 | 已加载规则在已扫描范围内未命中 | 同时保存 coverage、未扫描范围和后端状态 |
| 模型阅读官方章节与源码后的判断 | 模型评估结论 | MODEL_ASSESSED，附 reason/evidence |
| SDK/IDE 文件检查 | 语法与类型 | 实际命令、退出码、日志 |
| 完整构建成功 | 可编译、产物已生成 | receipt.json 与完整日志 |
| 包归档 | 阶段包存在且哈希固定 | 包路径与哈希 |
| 设备用例的业务断言通过 | 所测场景的运行行为 | 用例、实际值、日志/图片 |
| 文件哈希一致、结构校验通过 | 文件未变、格式合法 | 来源摘要 |

原因：用户依据报告决定是否发布，把低层证据写成高层结论会让未验证的行为进入线上。

### 二、原始逻辑行是唯一分母

用原始输入 SHA-256＋逻辑数据行序号建立 rowId。每个 rowId 恰有一条评估结论和一条处理结论，重复行各自保留。无需适配（含范围外）、可选适配、必须适配和待分类的合计等于原始逻辑行数。原始行、位置、物理文件、变更和工作单元分别统计。没有 rowId 的发现（U04a、U06a、扫描外发现及其获批修改）单独列出，原扫描分母保持不变。

原因：逐行对应是用户核对“每条扫描结果去哪了”的唯一依据。

### 三、任务数据经内置工具读写

读取、统计、定位和写入任务数据时使用下表入口，直接复用工具返回的原始行身份和路径。

| 需要 | 使用 |
| --- | --- |
| 解析原始 CSV、读取分组概要 | csv inspect |
| 取得某组完整 rowId、物理路径、调用、API 定义、版本与来源 | csv inspect --task --group <实际ID> --output <只读输入JSON> |
| 初始化分组 rowResults 与进度引用 | csv prepare --task --project --mode upgrade |
| 生成、校验、接收评估草稿 | draft-assessment、check-assessment、import-assessment |
| 统计与定位待处理行 | csv validate 的 pendingGroups；逐行定位加 --details --output，按 pendingFields 查原因 |
| 登记 RNOH 补充核对结论（U04a） | record-rnoh-review，返回已核对、已排除和待核对数量 |
| 生成 spec、记录批准或不实施 | prepare-spec、record-approval、record-decision |
| 更新处理状态与复核 | draft-resolution、update-resolution、reviewOnly |
| 生成结果表与报告、回读核对 | csv write 任务模式、report render --task、csv verify |
| 环境核查、完整构建 | inspect-environment、内置构建取证入口 |

原因：这些工具同时校验原表哈希、行身份和批准范围。自写的 shell 循环、grep 或临时 Python/Node 脚本绕过这些校验，得到的统计无法与交付件对账。工具结果与预期不符时，记录实际返回并按[排错](../common/troubleshooting.md)处理。

主 agent 是分组和进度的唯一写入者。评估 agent 只编辑自己的草稿，修复 agent 只编辑分配给它的文件。

### 四、决定只来自用户的明确答复

需要用户决定的事项见[用户决定](#用户决定)。把真实答复及其来源写入进度后再据此行动。未答复时对应字段保持 null 或 DECISION_REQUIRED，并继续做与该决定无关的只读工作。批准范围严格等于用户答复所指的条目、rowIds 和共享修改。

原因：修改源码、配置和运行设备测试都作用在用户的工程上，推荐项、预选项、沉默和超时都无法说明用户的真实意图。

### 五、缺口如实保留并继续

信息缺失、工具不可用、构建失败或 agent 中断时，写明具体缺口和下一步，已有充分依据的独立部分继续完成。

| 情况 | 记录为 |
| --- | --- |
| 来源、触发条件或源码无法确认 | EVIDENCE_GAP |
| 缺少业务决定 | DECISION_REQUIRED |
| 尚未处理 | PENDING |
| 未执行的构建或设备验证 | NOT_RUN |
| 用户明确选择不实施 | NOT_IMPLEMENTED |

零行、全部无需修改、待批准、中断或工具缺失时同样完成覆盖核对并交付真实结果。继续历史任务时按[恢复方法](../common/troubleshooting.md#断点继续)重新核对当前输入和实际批准，历史的成功结论、旧包和旧批准需要在本轮重新取得。

原因：带着明确缺口的部分交付可以继续推进，而被填平的缺口会在发布后才暴露。

### 六、只做获批范围内的最小修改

修改限于 spec 中已获批准的条目。保留任务外改动、原 compatible、原返回值与回调、异常传播、资源身份和生命周期。按 JSON5 解析并局部修改配置文件。实质方案变化时返回 U05 更新 spec；需要撤销时按实际差异逐处撤销。

原因：用户批准的是具体方案，范围外的改动没有经过评估，也无法归到任何原始行。

## 用户决定

| 时机 | 需要的决定 | 未答复时 |
| --- | --- | --- |
| U02，目标未明确 | 从真实配置和工具链支持的候选中选择 target，允许自行填写 | 目标与扫描区间保持待定，可继续独立环境核查 |
| U02，验证方式未明确 | 仅编译构建，不运行设备测试（推荐）；修改后设备验证（Beta）；前后对比验证（Beta） | 说明两个设备选项处于试用阶段；可能需要归档基线的源码和配置保持原样，可继续扫描与只读评估 |
| U05，spec 已形成 | 全部批准、明确部分、明确不实施或暂未决定；实施并选择设备验证时同时确认测试分类范围 | 源码和配置保持原样；任务开始时的“自动适配”只表示任务意图，具体方案仍需在 spec 上取得批准 |
| U06a，有效比对确认有未覆盖条目 | 是否补充评估 DevEco 规则包未覆盖的条目，选项依次为「否（推荐）」「是」 | 补充评估待用户决定，可按 U09 交付当前进度 |

提问与记录：

1. 优先使用宿主提问工具，缺少工具时等待明确文本答复。
2. 把真实答复及来源写入[进度](../../templates/progress.md)。已明确且仍适用的决定直接沿用。
3. 仅分析，或全部无需修改且没有配置修改计划时，spec 用于展示评估结论，此时没有需要批准的修复，只补齐已选择设备验证的范围。

部分批准与变更：

- 部分批准须唯一映射到条目、rowIds 和共享修改。共享修改涉及未批准范围时先向用户澄清。
- 范围、目标或实质方案改变时更新 spec 并重新确认受影响部分。同一获批方案的实现细节由执行者决定。
- 尚未答复的拟修复项保留 DECISION_REQUIRED。
- 用户明确选择不实施时，通过 record-decision 记录实际答复和方案 ID，所选行记 NOT_IMPLEMENTED，评估分类保持不变。NOT_IMPLEMENTED 与 NO_CHANGE、范围外含义不同，分别用于“需要但未做”和“不需要做”。

## U01 确定工程与范围

1. 进入子工程前记录宿主任务起始工作目录。
2. 范围明确后按[任务输出契约](../common/task-output.md)初始化一次任务，登记本次全部 HAR/HAP 工程，保存绝对 taskFile。已有本任务上下文时直接复用。后续追加工程先 register-project；未开始和失败的工程也保留在任务索引。
3. 读取真实根 build-profile.json5 的 products、模块注册及 module.json5。明确 product、模块/目录、工程类型、已有改动与验证范围。同类选择取并集，不同类型取交集。按物理路径核对符号链接、junction 和工程外注册模块。
4. 范围无法唯一限定时，列出实际候选并等待用户明确。
5. 保存原 target、compatible 和任务外改动。联合任务共享同一份原始基线，即两条任务开始前的配置值。

专题前置：

- HAR 先读[库与宿主](har-upgrade.md)，取得明确库范围和历史已适配基线。from 取历史已适配基线；库当前的构建 target 只反映构建配置。
- 工程依赖 RNOH 时先读[RNOH 专题](rnoh-upgrade.md#识别与基线)，以 harmony 目录为 HAP 工程根，在进度中记录 RN 版本、RNOH JS 包与原生 HAR 版本及形态、架构、JS 引擎、窗口设置和是否混合架构。

范围明确后进入 U02。

## U02 核对环境、目标与验证方式

**环境。** 拿到用户 SDK 路径或已知 DEVECO_SDK_HOME 后，按[版本契约](../common/sdk-versions.md#配置设备与打包字段)和[环境核查](../common/verification.md#环境与依赖)直接运行内置 inspect-environment（省略 --sdk 时读取该环境变量）。保存环境 JSON 和返回的 sdkRoot/sdkDefaultRoot/sdkPackagePath，供主/子 agent 复用。这一次调用同时核对 SDK/IDE 元数据、Node、Java、ohpm、Hvigor 和实际路径，SDK 元数据层级以它的返回为准。用户显式给出的工具路径无效时，报告该路径无效并等待更正。

**版本。** 分别记录编译 SDK、目标 target、compatible、精确扫描版本和设备行为版本，保留 Beta/Release 通道。版本满足 compatible≤target≤编译 SDK，各版本只升不降。API26 的配置值使用 26.0.0，扫描保留精确通道。target 由用户选择；CSV 终点和“最新 SDK”只作为候选展示。

**面向目标的预检。** 目标已知时用 `--to` 预检。扫描终点已确认时传入精确版本；仅确认 API 等级时先用该等级检查 IDE 门槛，SDK 覆盖按实际扫描终点核对。`devecoCompatibility.status` 为 `TOO_OLD` 时：

1. 向用户展示返回的 `message`，保留已选目标。
2. 暂停依赖该工具链的扫描、修改和构建。已有 CSV 仍可用于证据允许的只读评估。
3. 用户选定新 IDE 与 SDK 后重新检查，通过后继续原任务。

**扫描区间。** 应用的 from 默认取原 target，缺失时取原 compatible；HAR 显式提供历史 from。扫描区间为 (from,to]。`--from`、`--to` 直接传配置里的版本或 API 等级（如 `5.0.1(13)`、`26`），不带 Beta/Release 通道，由 scanner 按[配置与扫描](../common/sdk-versions.md#配置与扫描)展开成精确版本：起点取该 API 最早的通道，终点取实际 SDK 覆盖的最晚通道。不要自己补通道，同一个工程两次补得不一样，扫描区间和条目数就会不同；只有用户明确指定了通道才照写。展开后的精确版本以扫描结果返回的为准，后续记录和引用都用它。原 target 为 API12 时仍以 12 为起点以覆盖 API13，compatible 保持原值。保留原 target 且没有可信新增区间时，记录“无新增扫描区间”并处理已有证据；scanner 只接受 from<to 的区间，配置保持现状。

**验证方式。** 用户明确只评估不实施时，记录“不运行”并继续只读评估。其他任务按下表顺序展示选项，并说明两个设备验证选项处于试用阶段。已有明确选择时沿用该选择。U05 再依据实际分类确认必要用例范围。

| 展示名称（按此顺序） | 现有内部方式 |
| --- | --- |
| 仅编译构建，不运行设备测试（推荐） | 不运行；设备保持 NOT_RUN，不创建 runtime 运行，仍执行修复后的完整构建 |
| 修改后设备验证（Beta） | 仅修改后验证；runtime 使用 AFTER_ONLY |
| 前后对比验证（Beta） | 前后对比；runtime 使用 COMPARE |

验证安排按用户的真实答复登记。环境有缺口时，有充分依据的静态评估照常进行，未执行的构建和设备验证保留为缺口。目标明确后进入 U03。

## U03 扫描或导入并整理任务

**扫描或导入。** 先读取 scanner 真实 help，使用它实际支持的参数。复用 U01 的绝对 taskFile 和固定输出根，使用[目录与原件保护](../../templates/progress.md#建议目录)的实际返回路径。

```console
node "<skill-root>/scripts/scanner/bin/harmony-api-scan.mjs" help
node "<skill-root>/scripts/scanner/bin/harmony-api-scan.mjs" scan --task "<绝对taskFile>" --mode upgrade --project "<工程>" --sdk "<SDK>" --deveco-home "<IDE>" --from "<起点，不带通道>" --to "<终点，不带通道>" --product "<产品>"
```

- HAR/HAP 共享任务时间戳，各工程使用独立 ID。HAR 补充 --project-type har 及明确的 --scan-module/--scan-dir。RNOH 工程的 JS 工程不在 harmony 目录的上级或同级时补充 --rn-js-root。原生按实际能力准备编译上下文。
- 导入使用 import-csv --task，保留原字节与伴随来源。失败重试沿用同一任务时间戳。原始扫描表始终作为基线，adapted 表只是它的投影。
- 保存退出码、coverage、diagnostics 和超时/未扫描范围。分别表达无规则、未命中、后端失败和 CSV_ONLY 四种情况。

**读取扫描附带信息。**

- RNOH 工程按[扫描边界](rnoh-upgrade.md#扫描边界)读取扫描 JSON 的 `rnoh` 摘要，核对 `RNOH-` 业务行、框架依据状态和缺口，把缺口写入 scanEvidence.gaps。`rnoh.jsRoot` 为空或缺口提示未找到 RN JS 工程时，先按[识别与基线](rnoh-upgrade.md#识别与基线)新建任务并用 `--rn-js-root` 指定 JS 工程重新扫描，再继续整理。框架源码是只读依据，只有业务位置成为行。零行时仍进入 U04a。
- 读取扫描 JSON 或 coverage 的 `projectApplicability`。扫描器证实当前应用及扫描范围采用 Stage 模型时，会在生成 DevEco 本轮输入前排除 `CH2026010615012` 并记录配置证据。该条目仍计入规则包已覆盖，工程状态为 `EXCLUDED_BY_PROJECT_APPLICABILITY`，它已处理完毕，无需评估行或规则缺口评估。FA、混合或证据不足的范围保留该规则。Resource 类型扩展（`383`）按常规扫描。导入的历史 CSV 和本次实际命中保留全部原始行。

**整理为分组。**

1. 调用[内置 CSV inspect](../../templates/results.md#格式化接口与文件调用)，按[结果格式](../../templates/results.md)解析 BOM、CRLF、引号、单元格换行和 HYPERLINK。建立 rowId，保留原列、全部行及重复行。
2. 按规则身份/可验证来源＋精确版本归组，关联物理文件和调用点。未知身份、冲突、缺文件及范围外原因分别保留。按[官方资料定位](#官方资料定位)建立章节对应。
3. 运行 csv prepare --task --project --mode upgrade 初始化分组 rowResults 与进度引用。
4. 用 csv inspect 任务模式读取概要，再逐组以 --group <实际ID> --output <只读输入JSON> 取得完整行信息。
5. `csv prepare` 成功后，主 agent 先在返回的工程进度中写入版本，再进入评估或交付：
   - `versions.oldTarget`：修改前实际配置；未显式设置时注明由原 compatible 兜底。
   - `versions.target`：用户已确认的目标。
   - `versions.compatible`：本次确认的版本值；已核实的原最低兼容版本写入 `versions.oldCompatible`。
   - 扫描区间和编译 SDK 单独登记。原值依据不充分时记录“未知”及原因。

**评估接收与结果表的数据流。** 行为评估使用[固定评估接收](../../templates/assessment-results.md)：主 agent 为每组生成独立草稿，评估者按明确 rowId 集合填写，主 agent 接收后由工具直接展开到 rowResults。评估完成和处理结论更新后运行 csv validate（仅 STRUCTURE_ONLY 结构/一致性校验）。pendingCount 非零时按原则三定位原因，由模型处理真实缺口后再运行 csv write 任务模式。

行为结果表在去除 Fixed 的扫描列之后追加评估结论、处理结论、处理说明、后续事项：

- 评估结论按逐行 category 投影，范围外显示为无需适配。
- 处理结论使用无需适配、已适配、待决策、未实施。未评估和缺口暂列待决策，并说明原因及下一步。
- rowId、MODEL_ASSESSED 和准确内部状态保留在分组与报告中，CSV 只包含上述展示列。

**下一步。** 零行时跳过 CSV 逐行评估修复，进入 U06a。有可信独立候选时进入 U04；局部扫描失败时保留已取得的结果继续。完全受阻时进入 U09 交付。

## U04 按变更条目评估

**分派。** 按[变更评估 agent](../../agents/upgrade-assess-change.md)分派只读任务。向用户展示变更名称，内部保留准确规则、来源和版本。

- 每个变更条目由一个 agent 完整负责，包含它的全部关联文件和调用点；条目再大也保持为一个任务。
- RNOH 组合并：`RNOH-` 开头的各组交给同一个 agent，不受小条目合并的行数和个数限制。这些组共用同一个 RNOH 版本、框架基线和属性传递链，由一个 agent 读一遍 RNOH 专题并核对一次，比每组各自重读更快也更一致。合计行数多到单个 agent 难以完成时，再按规则拆成少数几个任务。每个组仍有自己的草稿、只读输入和官方章节，各自评估、各自校验。RNOH 组的只读输入自带框架依据和版本基线（`result.rnoh`）；派发时另把 U01 记录的架构（CAPI 或 ArkTS）、JS 引擎、窗口与混合架构情况和三方 RN 鸿蒙库清单写进提示，这些不在扫描结果里。
- RNOH 工程合批：分派前先由主 agent 完成 [U04a](#u04a-rnoh-无规则条目补充核对) 第一轮（不占用 agent），再把 U04a 第二轮的只读 agent 和本步骤的评估 agent 排进同一套批次一起派出。两类任务互不依赖，分开派要多等一整批。U04a 的任务按条目数当作行数参加排序，不算大任务。
- 小条目合并：行数不超过 5 的条目可以合并交给同一个 agent，每个合并任务最多 4 个条目。每个 agent 的固定开销（读说明、格式和案例索引）远大于评估几行本身，合并能减少 agent 数量和模型请求量。合并只是共用一个 agent：每个条目仍有自己的草稿、只读输入和官方章节，各自评估、各自校验。
- 并发数：由宿主的实际并发能力和当前模型的限流情况决定；用户指定了并发数时以用户的为准。遇到限流报错时把后续批次的并发数减半。只有行数超过 60 的大任务需要控制同批个数，同一批里只放少数几个：大任务起步时各自读入的输入多，同时起步容易触发限流，子会话可能长时间无响应。这个限制只针对大任务本身，其余任务不受它影响，每一批仍按宿主的并发能力派满。
- 分批步骤：一批要等其中最慢的 agent 返回才能派下一批，每一批还有读说明、读章节、写草稿这些固定耗时，所以批次越少越快。派出第一批前按下面的步骤排好全部批次，并把每批的任务列给自己核对一遍：
  1. 把全部任务按行数从大到小排成一列（合并任务按合计行数）。
  2. 从大的一头取任务放进当前批；按上一条，大任务够数后停止取大任务。
  3. 这一批还有空位时，从行数最少的一头取任务补满。小任务搭在大任务这一批里不会让这一批变慢，却能少开一批；不要把小任务留到最后单独成批。
  4. 剩余任务重复第 2、3 步，没有大任务的批次直接派满。

  例：10 个任务的行数为 213、83、75、29、26、23、16、12、8、2，宿主一批能派 6 个，大任务同批放 3 个。第一批是 213、83、75、2、8、12，第二批是 29、26、23、16，共两批。分成“三个大任务一批、中等任务一批、小任务一批”是错的，多开了一批。
- 向 agent 传入：draft-assessment 生成的独立草稿、该组只读输入 JSON 的绝对路径、完整关联文件/调用点和 rowIds、章节路径及起始行、工程上下文，以及主 agent 查[案例索引](upgrade-examples.md#案例索引)得到的命中情况（命中时给出案例正文路径，未命中时注明）。评估说明本身是自足的，派发提示里只需让 agent 读这一份说明，无需再列其他规则文档。评估 agent 需要这些原始输入才能逐行给出结论，主 agent 的摘要或代表文件无法支撑逐行判断。
- 已核实的共同配置证据可以关联多行，每个原始行仍各自保留归属及结论。尚未阅读的范围保持 PENDING。
- 宿主没有子 agent 能力时，向用户说明该能力缺口，由主 agent 按同一份说明逐条评估。

**评估内容。** agent 自己完整阅读官方章节，并读完主 agent 标明命中的案例正文。

- 准确命中已有案例时，分类前沿链接读完该案例的独立正文；只需读命中的案例。漏扫排错入口由真实错误/异常触发。
- 结合真实配置和调用落实触发/排除条件，在现有 reason/evidence 中保留证据或具体缺口。条件未触发时分类为无需适配并写明未触发的依据；“接受新行为”只用于条件已触发且用户选择接受的情况。
- 逐文件、逐调用分析，返回分类、证据、方案及缺口。
- 草稿顶层 changeSummary 保存供评估与方案使用的 before/after/targetIsolation/proposal，可选 business 保存本组业务概括，逐行 reportSummary 保存一两句核心理由。详细 reason/evidence 保留供核对。

**草稿流转。** 评估阶段工程源码和配置保持只读。

1. 评估 agent 编辑自己的草稿，用 check-assessment 只读核对。
2. 格式错误由原评估者用原生编辑修正，完整保留 knowledge.sources。
3. 主 agent 用 import-assessment 直接接收，通过 `--receipt-output` 保存并读取本次回执。草稿内容由原评估者负责，其他 agent 原样传递。
4. 某个 agent 失败或中断时，保留具体未完成范围，其他独立条目继续。补齐或明确记录未完成后，等全部任务返回再进入 U05。

**方案中的新增调用。** 提出修改方案时，按[新增调用规则](../common/arkts-coding-standards.md#新增调用的废弃状态)核对将要新增/替换的 SDK 调用及获取链，官方旧示例同样需要核验。同时核对真实 SDK 的同步抛错、Promise 拒绝、获取失败及回调失败，明确有效处理边界和业务失败出口，把必要改动纳入方案；已有外层处理可复用。核查范围是本次候选方案，原有的无关废弃代码保持原样。替代、最低版本或失败契约无法确认时，把准确声明、取舍和缺口写入现有 reason/evidence。

## U04a RNOH 无规则条目补充核对

仅 RNOH 工程执行。非 RNOH 工程跳过本步骤，其产物中不出现任何 RNOH 内容。

`RNOH-` 业务行在 U04 评估。本步骤按[RNOH 专题](rnoh-upgrade.md#补充评估方法)核对三类对象，判断它们是否经 RNOH 框架影响 RN 页面，每一条都要有结论。执行顺序上，第一轮在 U04 分派之前完成，第二轮的 agent 与 U04 的评估 agent 同批派出：

- 扫描 JSON 中状态为 `FRAMEWORK_ONLY` 的规则，以及 `BUSINESS_NOT_SCANNED`（业务 JS 未检索）的规则；
- `rnoh.uncoveredEntries` 中的条目；
- 三方 RN 鸿蒙库。

本步骤和 U04、U06a 可能遇到同一个官方条目，三者看的代码层不同，互不替代：

| 步骤 | 核对的代码 | 条目来源 |
| --- | --- | --- |
| U04 | 宿主 harmony 工程源码、RN 业务 JS | DevEco 规则和 RNOH 规则扫出的行 |
| U04a（本步骤） | RNOH 原生框架、RNOH JS 层、三方 RN 鸿蒙库 | 没有 RNOH 规则的官方条目、`FRAMEWORK_ONLY` 规则 |
| U06a | 宿主 harmony 工程源码与配置 | DevEco 规则包未覆盖的官方条目，用户选择补充评估时才做 |

本步骤只核对 RNOH 框架、JS 层和三方库是否把变更带到 RN 页面，宿主工程源码不在这里重看。DevEco 已在宿主代码扫出行的条目仍留在清单里：框架在 oh_modules 下，不在 DevEco 扫描范围内，它是否受影响只有本步骤会核对。

`uncoveredEntries` 通常包含区间内的大部分官方条目，其中多数与 RNOH 无关，所以分两轮处理。每条带有 `kit` 和 `category`（`ux` 为视觉与交互变更，其余为接口行为变更），第一轮先按 Kit 归类再判断：

1. **先整体过滤。** 主 agent 对整份清单执行补充评估方法的步骤 2、3（生效条件、按层过滤）。依据相同的条目成组排除，每组写明一条具体依据并列出组内全部条目标题，例如“以下条目属于方舟运行时变更，业务 JS 运行于 Hermes，不涉及”。Kit 只用来归类，排除依据仍是[代码层与适用变更](rnoh-upgrade.md#代码层与适用变更)里的具体事实；同一个 Kit 里有的条目涉及、有的不涉及时拆开处理。只有依据明确的条目才在这一轮排除，拿不准的留到下一轮。这一轮只看条目标题、Kit、官方章节的生效条件，以及 RNOH 专题里的分层表和已核实事实，不打开 RNOH 框架源码、三方库源码和业务 JS，也不为了多排除几条去检索。需要看源码才能判断的条目一律进第二轮：第二轮由 agent 并行处理，并且和 U04 的评估任务同批，多留一些条目几乎不增加总时间；第一轮是主 agent 独自串行做的，在这里检索源码会让整批任务晚派出。
2. **再逐条深入。** 过滤后剩余的条目、`FRAMEWORK_ONLY` 规则和三方 RN 鸿蒙库执行步骤 4–9，逐条记录生效条件、涉及层、文件与行号、证据等级（实证、推断、需真机验证）、结论和方案。

第二轮条目较多时，按涉及层或 Kit 分成几个任务，每个任务一个只读 agent，同一任务的条目共用一次框架源码检索；主 agent 把 U01 记录的 RNOH 版本、HAR 形态和架构传给它，并让它按登记格式直接写出 `reviews` JSON。这些任务与 U04 的评估任务按 U04 的分批步骤排进同一套批次，返回格式同 U04 的证据要求。分好任务后核对一遍：第一轮登记返回的每个待核对条目都恰好分给了一个任务。

记录方式（这些结果没有 rowId，按原则二单独列出）：

- 两轮的结论都用 `record-rnoh-review` 登记，格式见[记录与方案](rnoh-upgrade.md#记录与方案)。可以分多次提交，每次返回待核对数量和待核对条目；待核对数量为 0 才算完成本步骤，剩余条目会作为遗留事项进入报告。
- U05 方案 JSON 的 narrative 只写“RNOH 无规则条目补充核对”的概述（各结论的数量和需要处理的条目），逐条内容由报告从登记结果生成，不在 narrative 里重复。
- 需要修改或决策的条目写成 `rnoh-` 前缀的 sharedItems，并写明影响平台；登记结论时用 `sharedItemId` 指向它。
- 修改依赖目录、oh_modules 或 RNOH 原生框架属于需要用户批准的方案项。
- 整体性的未评估范围（如 release HAR 无法核对）写入 scanEvidence.gaps；逐条的需真机验证和证据不足由登记结果自动进入遗留事项。

完成后与 U04 结果一起进入 U05。

## U05 汇总 spec 并取得确认

**生成 spec。**

1. 等全部评估返回并完成接收，从实际 rowId 结果统计分类。
2. 主 agent 按[spec 模板](../../templates/upgrade-spec.md)填写业务正文与明确方案项，用[prepare-spec](../../templates/spec-results.md)在当前工程的 outputLayout.deliveryDirectory 生成 spec.md，汇总全部已返回结果及未完成项。
3. 方案项列出完整 rowIds，每个原始行只属于一个方案项。可选适配的同一批行若可选择保留旧体验或接受新行为，在同一方案项填写推荐做法和 `alternative`，让 spec 并列展示两种做法。原始行数与有证据的调用数分别展示，例如“14 条原始行，对应 12 处调用”。
4. 检查同一文件、公共 helper、配置和跨文件依赖的方案冲突。存在矛盾时回到对应 agent 补充，取得一致方案后再写入。

**spec 内容。** 写清分类、业务影响、逐文件修改方案或无需修改依据、保留原体验的方式与成本、共享修改、风险/替代方案、预期行为和验证安排，并纳入评估中必要的异常处理及业务失败出口。缺证据或缺业务决定的条目显式保留 EVIDENCE_GAP/DECISION_REQUIRED。

**取得批准。** 展示 spec 后按[用户决定](#用户决定)取得修复批准。

- 验证名称、推荐顺序及 Beta 说明统一沿用 U02；已有答复时展示实际选择。优先推荐“仅编译构建，不运行设备测试（推荐）”。
- 选择“修改后设备验证（Beta）”或“前后对比验证（Beta）”时，再确认设备测试范围：支持[三类](#分类与记录)任意组合及全部，建议覆盖全部并等待实际答复。所选的无需适配条目测试其正常功能。测试范围独立于修复批准范围和评估分母。
- 批准输入填写 prepare-spec 返回的实际方案路径、用户答复与来源、明确选中的 approvedItemIds。同组首轮选择任一已展示做法都沿用该 spec，每组只登记一个明确决定。用 record-approval 登记并读取本次 `--receipt-output` 回执。“接受新行为”与“获批实施修改”分别绑定当前评估和完整 rowIds，批准只覆盖答复指明的条目（例如批准某个 Dialog 的方案只作用于该 Dialog 的行）。
- record-approval 自动归档批准时的方案并同步确认区；失败时按实际回执重试同步。

**选择设备测试时的准备。** 取得必要答复后，按[白盒理解](../common/runtime-whitebox.md)从所选 CSV 调用点保存原始源码事实、明确行选择和 route-map.json。测试范围以所选 CSV 行为准。

**下一步。**

- 已批准：进入 U06。
- 明确不实施：记录决定，由用户在 U06a 选择是否补充只读评估，然后进入 U09，交付原扫描、spec、CSV 和 HTML。此路径下源码和配置保持原样，也没有修复包构建和修复设备验收。
- 未答复：保留待决策。

## U06 实施获批修复

**进入条件。** 有源码或配置修改时，需要 spec 相关方案已获批准且验证方式明确。无需修改时沿用已授权的测试安排。

**前后对比的基线包。** 选择前后对比时，在修改任何相关源码、配置和测试辅助源码之前：

1. 按[阶段包方法](../common/verification.md#行为前后对比)在原源码、原 target/配置下真实构建并归档 before 包。
2. 按[测试契约](../common/runtime-contracts.md)归档真实阶段包和输入哈希。模拟器直接使用实际未签名包。
3. 包构建、实际安装条件或归档不足以支持对比时，保存现场并等待补齐，或等用户明确改为“仅修改后验证”或“不运行”。验证方式的变更由用户决定。

before 包有效归档后即可开始修复，设备测试留到 U08，设备暂时不可用只影响 U08。联合任务先归档共同原始基线包，再实施影响它的共享修改。选择“不运行”或“仅修改后验证”时没有 before 包。无需修改的对比任务同样保留原包，源码保持原样。

**分工。** 依据实际待修改物理文件数、复杂度和并发能力，选择主 agent 直接修复或按[单文件修复说明](../../agents/upgrade-fix-file.md)分派，并简记理由。同一物理文件只有一个修改者，该文件的全部获批变更一起处理。共享 helper、配置和跨文件接口由主 agent 协调。主 agent 直接修复时执行同一份说明。

**实施与记录。** 按[编码规范](../common/arkts-coding-standards.md)、[行为兼容](upgrade-compatibility.md)及相关 HAR/原生资料实施最小修改。主 agent 使用 update-resolution 更新获批行：

- 原评估的 category/reason/evidence 保持原样，处理信息写入 resolution。
- 接受新行为：分类保持可选适配，outcome 记 NO_CHANGE 并追加决定依据。
- 未提供的 changes/next 保持原值，已有待办继续保留。
- 内部 MODIFIED 需要有与该行相关的实质业务差异。行为 CSV 显示“已适配”，处理说明写明三项：修改内容、作用、理由。
- 未编译、编译失败或人工验证尚未完成的，写入后续事项。“已适配”表示代码已改，验收状态由 U07/U08 的证据另行给出。

**新增调用的两项检查。** 主 agent 与文件 agent 都按实际 diff 执行。

1. 废弃状态。新增/替换的调用及其获取链使用未废弃的 API。官方旧示例提供行为依据，API 选择按[新增调用规则](../common/arkts-coding-standards.md#新增调用的废弃状态)核实当前 SDK、compatible 与有效 UIContext。找不到满足条件的 API 时，返回 U05 记录缺口或取舍，compatible 和告警配置保持原样。
2. 失败契约。检查新增或替换的调用、获取链和 helper：
   - 可抛异常的新调用由有效业务边界处理，已有外层 catch 可复用。
   - 框架回调内的异常在回调实际执行的边界处理；未 await 的 Promise 需要自己的拒绝处理或向有效消费者传播。
   - 处理后保留原返回值、后续语句、回调次数和资源释放。失败时走真实的业务失败出口。
   - 确认为不抛异常的同步 API 直接调用。
   - 检查范围是本次改动及必要调用链；依据不足时写明缺口。

修复者的返回结果列出四项材料：新增调用、SDK 失败契约、处理位置、复用或新增的处理方式。同一边界可合并说明多个调用。

**配置回读。** 实施后回读同一 product 的实际 target 和 compatible，把实施状态、回读值及证据位置写入进度的 `configurationImplementation`。已登记的原值和确认目标用于报告对照。未实施或配置保持原状时，记录本轮实际状态。这一步只写 `configurationImplementation` 这一个字段，进度里的其他内容保持原样。`decisions.repair`（方案与批准）和 `decisions.ruleGapReview`（规则缺口决定）由 prepare-spec、record-approval、record-decision、record-rule-gap-decision 写入，它们带有方案记录和哈希；手工重写会让后续的处理更新和方案生成报“缺少对应的当前批准方案”或“方案 spec 已变化”，批准要改时重新运行对应工具。

完成后进入 U06a，再统一进入 U07。

## U06a 按需处理DevEco规则包未覆盖条目

确定精确扫描区间后，scanner 已复用版本变更查询与实际同区间规则包条目比对，结果保留在扫描 JSON 的 officialComparison。“缺规则”以这份比对为准，CSV 未命中只说明已有规则未命中。

主 CSV 评估及获批修复结束后，按[补充处理](rule-gap-review.md)读取各工程的比对结果。来源缺失、变化或映射待核对时保留相应缺口。仅对有效比对中确认未覆盖的条目征求用户决定，展示各工程数量，并沿用仍适用的明确答复。

1. 提问「是否补充评估 DevEco 规则包未覆盖的条目？」选项依次为「否（推荐）」「是」。推荐理由是这类条目往往缺少可直接定位的 API 调用点，对应用的影响通常较小。
2. 用 `record-rule-gap-decision` 按工程登记明确答复。命令只接受 `--input <决定JSON>`，JSON 为 `{"action": "SKIP", "basis": "<csv inspect 返回的 ruleGapBasis，64 位十六进制>", "answer": "否（推荐）", "source": "<可定位的对话来源>"}`；用户答「是」时 `action` 写 `REVIEW`，详见[规则缺口评估](rule-gap-review.md)。RNOH 工程补充评估时，U04a 已核对过的条目直接引用它的生效条件和官方章节结论，本步骤只补宿主工程源码与配置这一层。用户选择「否」时跳过逐条评估，报告展示数量和跳过摘要。用户选择「是」时运行 `prepare-rule-gaps`，依据官方正文、当前源码/配置及真实 SDK 独立评估。确需修改时展示独立方案，按当前任务的实施范围另行取得批准。纯评估或不实施任务在获准补充后只做只读评估。
3. 补充处理结束、用户明确跳过、确认未覆盖条目为零或暂时无法取得有效比对时，按已授权范围进入 U07。纯评估或不实施任务进入 U09。用户尚未答复时保留待决定，可按 U09 交付当前进度。

## U07 复核与完整构建

**更新前回读。** 更新处理状态和验证待办前，回读当前分组哈希，按固定契约记录具体处理/验证说明。仅更新验证待办时业务 outcome 保持不变，也无需修复批准。

**静态复核。** 主 agent 按[静态复核](../common/verification.md#通用静态复核)核对实际 diff、SDK 声明、官方触发条件、资源/回调身份、异常和生命周期及配置。

1. 再次复核新增调用、helper 及获取链的废弃状态和相关新增告警。这项复核独立于构建结果，因为使用废弃 API 的代码同样能构建成功。
2. 对照实际 diff、准确声明及修复者返回的四项材料，逐项核实新增调用的失败契约与实际处理位置。重点检查同步异常、await 拒绝、框架回调和未 await Promise 的有效边界，以及正常/失败路径的返回、后续语句、回调次数和释放。这项复核同样独立于构建结果。
3. 遗漏处理的返回 U06 修正；无法核实的契约或业务失败出口记录具体待办。
4. 通过 reviewOnly 把复核说明、准确声明及替代选择追加到已有 resolution.review，原评估 reason/evidence 保持原样。验证记录中分别记录模型复核、实际检查及构建。
5. 原生核对实际 ABI 和构建上下文，HAR 核对宿主 target 和真实消费。

**完整构建。** 每轮源码或构建配置修改后，由主 agent 统一构建一次：

1. 按[完整构建](../common/verification.md#完整构建与产物)使用内置构建取证入口，在对应工程根安装依赖；安装成功后执行已选 Hvigor 参数。安装失败时本轮以 INSTALL_FAILED 结束。
2. 保存命令、日志、退出码和本次对应产物。按[验证引用](../../templates/assessment-results.md#工程级验证引用)使用构建返回的 `result.receiptPath` 登记本次回执和明确覆盖行。通过/失败只在这一处登记，各行和报告引用它。
3. 设备验证使用最终 after 包；after 的归档副本与 before 分开存放。
4. HAR 先构建库，证明本次消费，再构建宿主。
5. RNOH 工程修改业务 JS 或 JS 层补丁后，先清理 Metro 缓存并重新生成 bundle，再构建 harmony 工程，见[RNOH 构建与验证](rnoh-upgrade.md#构建与验证)。Hvigor 只打包 rawfile 里现有的 bundle，不编译业务 JS，所以构建成功不能说明 JS 修改有效。构建回执的 `rnBundle.status` 为 `FRESH` 时，JS 修改行才能引用本次构建；其他状态下先重新生成 bundle 再构建，做不到时这些行的验证记为未完成并写明原因。
6. 未修改时按已选验证范围安排必要构建。

**失败处理。** 代码失败时只修必要闭包，然后回 U06/U07，按[排错](../common/troubleshooting.md#定位与停止)限制实质失败方案的次数；环境阻断不计入源码方案次数。构建未成功时按部分完成交付，产物和通过结论以本轮为准。

选择设备验证时进入 U08，否则进入 U09。

## U08 按需测试与报告

**生成用例。** 按[功能取证](../common/runtime-functional-tests.md#行为前后对比)使用 CSV 选中行、原始白盒事实和获批 spec，依次完成全部四步：生成 test-spec.json，生成 test-cases.json，生成并校验 Hypium JSON 操作清单，冻结完整 run 快照。每一步的产物是下一步的输入，也是报告逐行反查的依据。

**执行。**

- 对比模式先测试归档的 before 包，复位约定数据后测试 after 包。仅修改后验证只测试 after。
- 两个阶段使用同设备/系统、同语义用例和可复位数据。优先使用两个包都支持的外部操作，因为 before 包里没有本次新增的测试入口或埋点。
- 按[测试契约](../common/runtime-contracts.md)运行内置工具，操作与采集统一通过 Hypium。按[视觉判定](../common/runtime-visual-judgment.md)使用当前宿主读取实际图片。
- 保存证据后清理本次启动的实例，其他实例保持原样。

**报告。** 由审计产物生成 test-report.html，逐行反查完整来源/rowId、测试点、用例、阶段包、业务断言、实际值、日志/图片和差异。[测试报告模板](../../templates/upgrade-test-report.html)规定展示内容，通过与否取自审计产物。业务正确由业务断言判定：before/after 表现相同只说明没有差异，截图或成功启动只说明页面可达。

**受阻时。** 包缺失、数据不可复位、测试入口不兼容、设备或工具不可用时，分别报告实际到达的阶段及不可比范围。before 包只来自修改前的归档；没有归档时该对比记为不可比。

**更新处理记录。**

1. 用 draft-resolution 按已批准方案或明确行生成草稿，用原生编辑填写实际差异、复核证据及剩余 next。通过 `update-resolution --receipt-output` 提交并读取本次回执。
2. 已完成的待办或说明性文字，通过 reviewOnly 带真实证据关闭。
3. 之后源码/配置再变化时，重建 after 并重测受影响用例；before 归档保持原样。
4. 设备和测试失败时保留可信修复，对比结论如实记为失败或不可比。

所有结局都进入 U09。

## U09 覆盖核对与交付

**核对版本记录。** 生成报告前逐工程核对 `versions.oldTarget`、`versions.target`、`versions.compatible` 和 `configurationImplementation`。用本轮基线、明确目标和配置回读补齐有依据的字段。仅评估或明确不实施时写明实际状态；依据不足时在遗留事项保留缺项。修改版本记录后重新生成并核对报告。

**生成结果表。**

1. 确认全部接收/更新已返回，且没有后台写入者。
2. 按[行为结果格式](../../templates/results.md#行为结果与可选测试截图)调用[内置 CSV write任务模式](../../templates/results.md#推荐数据流直接从分组输出)，从分组 rowResults 生成 UTF-8 BOM 与 CRLF 的结果表。逐行判断与报告分类由此同源。原扫描表保持不变。
3. 回读核对：评估结论与分组分类一致；处理结论和单行处理说明一致；原字段与重复计数保留；设备测试的截图列在最后。
4. 再回读原始行、分组和文件证据，核对来源/精确通道、完整章节的实际阅读范围、分类、批准和真实差异。
5. 按原则二核对分母和各项统计。每行的结论需要该行自己的依据，同文件其他位置的变化只算作其他行的依据。归因到某条内置文本变更时需要该变更的触发依据；普通 Text 设了固定高度这一事实单独不足以归因。

**生成报告。** 主 agent 按[固定报告命令与输入](../../templates/html-reports.md#固定报告命令与输入)直接调用 report render --task --mode upgrade（省略 --data）。工具在同一次读取中取原扫描、分组、进度和验证证据，共同生成 CSV 与 HTML，保留[行为 HTML 模板](../../templates/upgrade-report.html)完整样式，产出唯一的 api-adapt-report.html。

- 按任务索引纳入本功能全部参与工程，包括失败或未开始项。各工程分节引用自己的 spec.md、进度、CSV 和 runtime 返回实际地址的 test-report.html。
- 联合构建和宿主测试只引用一次。每个工程的缺口单独呈现，其他工程的通过结论只适用于其自身。
- 首页展示实际配置旧→目标及最低兼容版本；配置实施事实由进度保存。
- 编译事实引用本轮成功构建的 receipt.json 及完整日志，旧 INSTALL_FAILED 单列保留。手动命令成功而标准回执缺失时，记为“取证缺口”并写明手动命令的实际结果。
- 评估、修改、包归档、完整构建、设备测试和有效对比按原则一分开呈现。只有每一层都有本轮证据时才写“全部完成”，否则写明已完成到哪一层。
- 核对首页实际改动和待处理提示，再展开详情回读逐行结论、批准及全部文件链接。清除模板提示。另存时在进度中记录实际报告路径。

**报告版式。**

- 按模板统一总览字段顺序；工程章节为“工程名称 · 评估与修复”。
- RNOH 工程的 `RNOH-` 分组由工具自动移入独立的“RNOH 业务影响分析”章节；非 RNOH 工程没有该章节。
- 每个变更条目保留准确官网链接，标题下集中展示评估与修复统计。DevEco 覆盖条目有明确的官方前后对照时引用原文或对照表；仅有变更影响时，摘要只展示 target 隔离状态和明确门槛。工程触发条件和兼容判断保留在详情。
- 折叠区逐原始 CSV 行展示完整 rowId、代码位置和结果。处理说明默认显示模型写的 reportSummary（一两句概括核心理由及处理），同单元格“完整依据”折叠保留处理说明全文和段落。
- 业务与触发使用 changeSummary.business 的一至三句总结，由模型针对本组撰写。
- 旧任务缺少简述时用[summaryOnly更新](../../templates/assessment-results.md#仅更新html简述)补充，由模型撰写简述；该更新只改简述，分类、批准、真实差异、next 和复核标记保持原样。缺少简述或决定过期/待复核时，报告回退显示完整依据。
- 保留完整 rowId、重复行和处理说明文字。CSV 只合并处理说明内的换行，取材证据继续保留。

**关键决策与批准展示。** 首页在原有评估总数下分别列出当前获批修复和接受新行为的行数。关键决策点按工程和变更展示有明确用户答复的方案项，读取已登记的方案说明、实际 rowId 范围和决定。完整答复与来源折叠保留。只评估、待答复、共享配置和过期决定不入卡。旧任务的 keyDecision 字段可读取，报告以可核对的决定记录为准。

**测试建议与遗留事项。** 生成前主 agent 在各工程 progress.testSuggestions（可选字符串数组）保存针对性测试建议：

- 每项说明实际页面/功能、操作场景、预期结果及适用设备或版本，针对本工程编写。
- 结合已修复、接受新行为及尚未验证的影响，覆盖功能、视觉和兼容回归。
- RNOH 工程同时覆盖 U04a 中需真机验证的项；涉及共享 JS 的修改注明 iOS 和 Android 回归。
- 存量告警等维护问题归入遗留事项。

报告末尾统一展示“遗留事项与测试建议”：两部分上下排列、独立折叠且默认收起，标题显示条数，打印时完整展开。按工程合并实际缺口、完整逐行后续事项及旧 nextSteps，保留行身份并去除完全重复内容。同批次扫描证据接在对应缺口条目末尾。测试建议是给用户的建议，与逐行 next（实际待办）和设备测试授权相互独立。旧任务缺少建议时如实显示；后续补充后重新生成并核对报告。

**回读验证。** 报告返回后用 `csv verify --receipt-output` 核对原表、当前分组、结果表和报告来源摘要，并读取完整回执文件。源评估受保护字段不一致、存在旧快照或发布后发生变化时，交付视为未完成，修正来源后重新生成并再次 verify。旧来源未建立时保留缺口。

**最终答复。**

- 直接引用 verify 的 categoryOutcomeCounts 和 acceptedNewBehaviorCount，分别呈现各评估分类的处理结果和实际接受新行为数量。
- 回读 pendingCount、unresolvedCount、nextCount、reviewCount 及 gaps，分别说明未决、待办和复核情况。存在比对来源时另报 ruleGapCount、ruleGapAssessedCount、ruleGapPendingCount、ruleGapSkippedCount 和 ruleComparisonPendingCount。
- 用户修改过的交付件另存为新版本，原文件保留。

## 官方资料定位

**定位章节。** 新扫描 CSV 保留 Rule ID 和 Changed in SDK，详细 Source Reference 从同批次扫描 JSON 读取，按每组自己的真实记录取得。读取[本地索引](../changelogs/changelogs-index.json)，按 documents.path 的当前路径定位：文件部分相对本 skill 的 references/changelogs，保留章节行号，用 node:path 构造物理路径以兼容分隔符。历史路径和别名保留原值，只有当前路径用于定位。取材复用 loadChangelogIndex 和现有版本函数。

**核对身份。**

- 核对 CSV 与 JSON 的批次、模式、可见字段及重复次数。upgrade 的 findings 保持扫描行序；同位置的多条记录各自保留，即使结果表删去了列号。
- 仅有 CSV 时，使用 Title 的官方链接、规则身份、精确版本和源码补证。历史 CSV 有 Source Reference 时保留原值。
- 核对准确标题、来源及保留 Beta/Release 的版本。7.0.0(26) Beta1、26.0.0 Beta1 可按现有版本能力归一到 26.0.0(26) Beta1；Beta1、Beta2、Release 是三个不同版本。
- 无规则 ID 时只接受唯一可验证来源，标题只辅助定位。
- 无法唯一确认章节或身份冲突时，保留原行并记录 EVIDENCE_GAP。

**阅读范围。** 完整章节包含原因、影响、生效条件、接口清单和适配指导，读取直到代码围栏外下一个同级或更高级标题。评估 agent 需要自己读完正文；scanner 读过资料、CSV 链接或摘要都只是定位线索。仅在本地缺失、歧义或与真实 SDK 冲突时补充官方网页，并记录本地已查路径/范围、缺口、准确 URL、实际阅读范围、补充内容及差异。本地原件保留；未解决时仍为 EVIDENCE_GAP。

## 分类与记录

| 分类 | 依据 |
| --- | --- |
| 无需适配 | 未触发、已符合指导、原调用满足要求或仅需重编译，有具体源码和官方依据。 |
| 可选适配 | 接受新行为或保留旧体验均符合已知业务要求；默认提出保留旧体验的方案并说明成本，交由 spec 确认。 |
| 必须适配 | 已有证据表明会破坏所需业务、契约或编译正确性，需要具体修复；分类之后仍需用户批准才实施。 |

**分类规则。**

- 分类以调用为单位：同一变更的不同文件、同一文件的不同调用可以分类不同。
- 证据或决定不足时使用原则五的状态（EVIDENCE_GAP、DECISION_REQUIRED），三类只用于依据充分的行。
- 用户明确接受新行为且符合业务约束时，可依真实依据记 NO_CHANGE。用户只是拒绝授权修改时记 NOT_IMPLEMENTED，该行是否需要修复仍以评估分类为准。

**内部状态与 CSV 展示的对应。** 两者独立维护，展示值由内部状态单向投影得到；判断适配必要性或验收状态时读取内部状态和证据。

| 内部处理状态 | CSV 处理结论 |
| --- | --- |
| NO_CHANGE、OUT_OF_SCOPE | 无需适配 |
| MODIFIED | 已适配 |
| NOT_IMPLEMENTED | 未实施 |
| PENDING、DECISION_REQUIRED、EVIDENCE_GAP | 待决策，在处理说明和后续事项中区分原因 |

原始 rowId、内部状态、MODEL_ASSESSED 及完整证据保留在分组与报告中。

**进度。** 复用[通用进度](../../templates/progress.md)：

- decisions.repair.plan 指向实际 spec.md，answer/approvedItems 保存真实批准。
- runtime 保存方式、分类范围、答复和必要的 baselineDecision。
- 包路径/哈希、构建和实测证据分别关联 evidence，各自按原则一表达。
- 未答复保持 null，未执行保持 NOT_RUN。

**各组 knowledge。**

- originalReference：保留实际输入证据中的 Source Reference 原值，并注明来自扫描 JSON 或历史 CSV；没有该字段时留空。
- localReference：已核实的当前章节路径及行号。官方 URL 另存为来源证据。
- rawVersion/version：原始/规范化的精确版本。
- readRanges：只登记工具真实读取的 path/startLine/endLine。留空表示尚未读取。
- supplements：补充官方网页时记录 reason/url/readRange/content/difference。

各文件 reason/evidence 保存实际实参/默认值、触发判断、SDK 和源码位置，并落实准确命中的[案例](upgrade-examples.md)条件；只写与本条相关的内容。尚未处理的保持 PENDING。

**rowResults。**

- 按完整原始 rowId 记录独立的 category/outcome/reason/changes/compatibility/evidence/next。分类与处理结论分别维护。每行恰有一个来源，身份已知。
- 旧 rowClassifications 只用于兼容核对；与 rowResults 冲突时先修正分组再输出。
- 文件 adaptationCategory 仅在全部行分类一致时填写，否则为 null。三类统计以逐行分段为准。
- 历史原表中的 Fixed 随原字节留档。行为结果由当前逐行评估和处理记录投影。
